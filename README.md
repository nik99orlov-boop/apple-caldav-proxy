# Apple CalDAV Proxy

Маленький сервис на Python (FastAPI + библиотека `caldav`), который берёт на себя
общение с iCloud CalDAV — потому что HTTP Request нода в n8n получает от Apple
обрезанный/пустой ответ даже с правильными credentials, а `curl` и Python-библиотека
`caldav` с теми же данными работают нормально. Подробности — в документе проекта
`n8n-apple-calendar-integration-2026-07-31.md`.

n8n дальше ходит в этот сервис обычным JSON по HTTP — никакой возни с CalDAV/XML
внутри n8n не остаётся.

## Статус

**Код не протестирован живьём** — у этой сессии никогда не было настоящего Apple ID
и app-specific пароля (они всегда оставались только в n8n credential, сюда не
передавались — так и должно быть). Логика написана по документации `caldav` и
рабочим примерам из её репозитория, но первый реальный запуск нужно будет
проверить руками (см. «Проверка» ниже) сразу после деплоя.

## Вариант A — Render.com (без своего сервера, бесплатно)

Выбран как основной вариант — не требует ни VPS, ни иностранной карты для
регистрации. Минус: бесплатный сервис «засыпает» после 15 минут простоя, первый
запрос после паузы будет с задержкой ~30-60 секунд (Render поднимает контейнер
заново), дальше — быстро, пока не уснёт снова. Для личного календарного инструмента
это не критично.

### 1. Выложить код в публичный репозиторий на GitHub (без командной строки)

1. Зарегистрироваться на github.com (если аккаунта ещё нет) — обычная почта, без
   карты.
2. Создать новый репозиторий (New repository), например `apple-caldav-proxy`,
   отметить **Public** (обязательно — приватный репозиторий Render без платной
   подписки не подхватит по прямой ссылке).
3. Через кнопку **Add file → Upload files** на странице репозитория перетащить
   все файлы из присланного архива: `main.py`, `requirements.txt`, `Dockerfile`,
   `README.md` (сам этот файл можно не грузить — не обязателен). `.env.example`
   грузить не обязательно, а вот `docker-compose.snippet.yml` можно оставить —
   Render его игнорирует, пригодится позже для REG.RU.
4. Commit changes.

### 2. Создать Web Service на Render

1. Зарегистрироваться на render.com (можно через GitHub-аккаунт из шага 1 — тогда
   меньше кликов).
2. New → Web Service.
3. Выбрать **Public Git Repository** и вставить ссылку на репозиторий
   (`https://github.com/ваш-логин/apple-caldav-proxy`) — не обязательно
   авторизовывать доступ к GitHub-аккаунту через OAuth, просто ссылка на публичный
   репозиторий.
4. Runtime — **Docker** (Render сам увидит `Dockerfile` в репозитории).
5. Instance Type — **Free**.
6. В разделе **Environment Variables** добавить:
   - `APPLE_ID` — тот же Apple ID, для которого создавали app-specific пароль
   - `APPLE_APP_PASSWORD` — сам app-specific пароль
   - `PROXY_TOKEN` — любая длинная случайная строка (можно просто настучать по
     клавиатуре 40+ символов, или сгенерировать где угодно)
   - `APPLE_CALENDAR_NAME` — опционально, если нужен не первый календарь в списке
7. Create Web Service — Render соберёт образ и задеплоит. Займёт пару минут.
8. Скопировать публичный адрес сервиса (вида `https://apple-caldav-proxy-xxxx.onrender.com`)
   — он понадобится дальше для n8n.

### Проверка

```bash
# health (без токена)
curl -s https://apple-caldav-proxy-xxxx.onrender.com/health
```

Должно вернуть `{"ok":true,"calendar":"<имя календаря>"}`. Если ошибка — текст
будет от самой iCloud/caldav библиотеки, что уже подскажет причину (в отличие от
пустых ответов, которые мы видели через n8n напрямую). Пришлите мне ответ — я
подключу этот адрес к воркфлоу 10 в n8n.

## Вариант B — свой сервер (REG.RU, вместе с self-hosted n8n)

Если/когда всё-таки решите поднять VPS — тот же код разворачивается через
`docker-compose.snippet.yml` и `.env.example` в этой папке, без изменений (порт
внутри контейнера остаётся 8090, наружу не публикуется — только n8n достаёт его
по внутренней docker-сети). Инструкция была в предыдущей версии этого README,
принцип тот же: скопировать папку на сервер, добавить сервис в общий
docker-compose, заполнить `.env`, `docker compose up -d --build`.

## Проверка остальных эндпоинтов вручную

```bash
BASE=https://apple-caldav-proxy-xxxx.onrender.com   # или http://localhost:8090 для варианта B
TOKEN=<значение PROXY_TOKEN>

# список событий
curl -s -X POST $BASE/events/list \
  -H "X-Proxy-Token: $TOKEN" -H "Content-Type: application/json" \
  -d '{"date_from":"2026-08-01T00:00:00+03:00","date_to":"2026-08-31T23:59:59+03:00"}'

# создать событие
curl -s -X POST $BASE/events/create \
  -H "X-Proxy-Token: $TOKEN" -H "Content-Type: application/json" \
  -d '{"title":"Тест","start":"2026-08-05T14:00:00+03:00","end":"2026-08-05T15:00:00+03:00"}'
```

## Дальше — подключение к n8n (воркфлоу 10)

Как только `/health` отвечает `ok:true` — возвращаемся к воркфлоу
«10 — Calendar Actions» и меняю там Todoist-ноды (Create/List/Update/Delete Task)
на HTTP Request ноды, которые зовут этот прокси по публичному Render-адресу
(или внутреннему docker-адресу для варианта B), с заголовком
`X-Proxy-Token: {{ $vars.APPLE_CALDAV_PROXY_TOKEN }}` — значение добавлю в `$vars`
n8n рядом с остальными (`BITRIX_WEBHOOK_BASE_URL` и т.п.).

Этот шаг я сделаю сразу после того, как вы пришлёте рабочий ответ `/health` — чтобы
не менять живой рабочий Calendar Tool (сейчас на Todoist) на что-то непроверенное.
